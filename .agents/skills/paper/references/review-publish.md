# 成组审阅、可见候选与正式提交

## 形成具体候选

对于已有 workflow run 的实质科学候选，唯一交付门为：所有适用科学边界接受、最终候选/来源哈希与报告一致、**实际 final_review 通过**、共享修改责任确认、同组机械校验通过、具体用户授权覆盖当前内容。`candidates`、review stage 与 publish 均检查同一门，integration.finding 不能代替 final_review。独立的手工编辑提案继续使用既有审阅功能，不伪造论文 workflow。

首次最终候选由全新上下文的实际独立执行者按对应能力的科学与展示门完整审阅，默认请求中档；仅在中心机制冲突、证据归因争议或难判替代解释可能改变主要裁决时追加高档定向复核。责任 owner 核证会改变中心结论的关键原页。返工后先比对绑定的旧/新候选哈希与具体 diff，若仅改局部图边、口径或段落，则由可隔离上下文的审阅者只读旧问题、改动和受影响原页，记录仍有效的门与重审的门；责任 owner 再核中心结论。改动跨越机制、证据对象或主要裁决时重做完整独立审阅。所有复核及返工计入全树成本，不能用局部复核冒充初次完整审阅。

最终科学复核给具体问题、决定性来源、发现与判定，并绑定候选及来源快照。它不重新完整精读，也不是机械 checker。缺失、拒绝或过期均不能发布；用户编辑候选后按实质变化重审受影响判断。无增量 K 检查没有新候选，只保存具体不变依据及同组影响检查，不另起空审查代理。

每个最终目标有唯一候选写者与一个现行版本。知识建议以目标/基线候选哈希/片段/依据/科学确认责任形成局部 diff，写者整合后旧稿只作历史；目标或来源变化使旧整合失效。实际局部整合由唯一写者的 `workflow integrate` 绑定，接口见 [知识成文](../../paper-knowledge/references/composition.md)；整合后成文 checkpoint 和最终复核重做受影响部分。先完成科学核验，再由对应作者修正关键解释；格式工具不能编造缺失机制。候选组包括论文/对比/专题及确有变化的知识，保留既有稳定身份、锚点、独特有效解释和用户原话。

内部草稿在 `.research/drafts/<run>/`。用 `review stage --proposal 标识 --run 运行 --drafts 映射.json` 暂存；映射是正式Markdown路径→内部草稿路径。也可用 `--changes` 提供正式路径→完整正文/null；删除须属于明确任务与授权。新候选给简洁kind，旧正式页不因模板变化全量改写。

脚本按最终路径检查同组出链及既有入链、块ID、源版本和固定材料；合法格式在审阅前完成。`check --changes` 及stage/import/publish按本次改动校验：新增错误、改动页自身错误、受影响的既有入链、所用固定来源及显式语义契约必须通过；未变化且不相关的历史错误单列保留，不声称全库通过。提交后仍与提交前全库基线核对，新的其他错误也阻止并回滚。普通导航不当证据，机械通过不等于科学通过。

## Obsidian待审交互

`review stage/show/import` 返回当前 `审阅/<proposal>/r0001/总览.md` 等修订入口，候选页保留正文和原生块锚点。同组被改目标映射到候选，其他目标与固定附件仍指正式内容。待审属性和目标只用于投影，正式索引/Bases仅包含三个正式目录。

展示完整候选、具体diff、目标及实质变化/未知。总览只交代本组为什么改、影响哪些页和未决项；科学判断留候选正文，不在总览再生成判断卡、证据清单或逐段摘要。用户在Obsidian编辑候选后，先 `review show --proposal …` 查看变化，再 `review import --proposal …` 读回；它读取固定编辑快照，生成**新的修订目录**，保留旧视图。内容变化后使旧候选哈希绑定的科学复核及机械缓存失效，按实质变化重核受影响判断及实际授权范围；不复用旧 final_review。workflow 关联候选的 scientific_binding 失效后，核候选并重新暂存当前有效版本，再提交。旧修订合并后又有编辑时也阻止提交：协调者先将该修改与当前候选人工合并或明确保留理由，再用 `review import --acknowledge-retired '实际处理说明'` 登记，脚本不自动舍弃旧修改。正式页同时发生修改时停止自动合并，由协调者读最新原文、保护原话并形成具体候选。

视图生成失败时保留可查的 `preparing/staging_failed` 记录；读取具体候选后可 `discard` 并以新提案重建。提交失败保存独立 attempt 与前稿，已回滚且没有新冲突时允许重试，不因失败日志存在永久锁死提案。

文本围栏树状总览用于阅读，点击入口放图后；原生块ID不隐藏或重命名。未实际看过界面就说明未做界面验收。

## 授权与提交

用户确认一次具体改动组即可；已有明确授权涵盖的内容不重复请求。digest只绑定候选，不能代表人类授权。发布前重新读正式文件与候选，记录真正的用户授权及范围。

`publish --proposal … --digest 当前摘要 --authorization 实际授权说明` 提交批准内容。脚本拒绝编辑后未合并的投影、过期摘要、源定位错误和正式冲突；保存修改前内容及提交记录。Obsidian不参与工具事务锁，提交过程外部编辑冲突须保护并报告，不能静默覆盖。

发布后做结构检查及任务需要的实际阅读路径核验；科学结论、用户理解和独立实验复现不能由这些检查推出。

## 完成与清理

工作流完成后用 `workflow report --run <run> --unit <unit> --finding <实际finding.json>` 记录实际 final_review（`decision:accept|revise`、`review_kind:final_review`、`reviewer/summary/checks`及实际依据），再用 `workflow candidates --run … --finding '实际成组语义/知识增量核验'` 取唯一候选组；finding 不是科学复核的替代。其候选映射的 `version_ref` 指向不可变历史版本，`draft` 与 `sha256` 核对唯一现行稿；`target_sha256` 同时核正式目标基线，外部新编辑须先合并而不能覆盖。映射经 `review stage --drafts` 保留草稿路径与完整哈希。`finish --run …` 要求所有所选科学轮已接受或有具体不适用理由、每份最终候选已提交或明确废弃；单个提案处理完不能清理仍运行的其他单元。待审继续保留。明确废弃先 `review discard --proposal … --reason …`，再按授权用 `finish --run … --discard`。提案与run不同时，stage显式关联run。没有工作流的独立提案也可按自己的run清理。

固定来源、证据定位/覆盖、真实查询/筛选、重要知识更新、接受产物的历史版本、完整审阅修订、提交前副本与提交记录持久保留；它们不属于执行缓存。归档按路径和哈希绑定真实版本，不能把旧判断指向同路径的新内容。清理先核所有归属及符号链接、完成档案再删除；中断可用同一finish接续，归档后发现新编辑则保留工作目录。已完成run的 `workflow status/recovery` 可只读查档，新研究使用新run。无新认识就记不变，不制造认知进展。未结束的其他运行、迁移快照和评估冻结首稿不由finish删除。

finish 不以发布前旧目标基线核发布后的页面；它核实际提案、提交记录及现行批准正文。仍在交付的 owner 或 reserved/bound 助手会阻止清理；已提前保存的 report/helper 版本须有状态中的哈希绑定才能留在同一持久档案。正式页新编辑、未绑定记录或部分归档保留原文件，不能为完成清理覆盖或删除。

用户明确要求清除并重新研究一个中断运行时，先真实停止所有相关代理并登记 interrupt，再用 `finish --run … --abandon-reason '真实授权与原因'`。此路径拒绝执行中的科学轮、待审提案和归属不明目录，完整归档旧工作及其哈希引用后清除临时目录；旧轮保持原接受/中断状态，不标记研究完成。固定来源、历史对照和其他运行保留；按来源共享的图像缓存只在确认无其他使用者且用户要求时另行定向清理。
